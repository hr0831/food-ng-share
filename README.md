# ふたりごはん

ふたりで「自分が食べられないもの・苦手なもの」を共有するための Web アプリです。
外食やホームパーティの前に、お互いの NG 食材をスマホからすぐ確認できます。

画面上部で **「にがて」と「すき」** を切り替えます。にがて側はミント、すき側は桃色に
配色ごと変わるので、いまどちらを見ているか一目で分かります。

- 利用人数: **2人**（自分と友人1名）
- 端末: スマホ想定（iOS Safari 16+ / Android Chrome）
- 構成: **GitHub Pages（静的ホスティング）＋ Supabase（DB・認証・リアルタイム）**
- フレームワーク・ビルド工程なし。HTML / CSS / Vanilla JS のみ

---

## ⚠️ はじめに（アレルギー情報の扱いについて）

このアプリはアレルギー情報を扱いますが、**あくまで参考情報の共有ツールです。**

- 実際の注文時は、**必ずお店へ直接口頭で伝えてください**
- 微量の混入や調理器具の共用まではこのアプリでは管理できません
- 相手の登録内容が最新である保証はありません（登録漏れ・更新忘れがあり得ます）
- 生命に関わる重度のアレルギーがある場合、このアプリだけに頼らないでください
- **削除は確認なしで即実行されます。**「元に戻す」は5秒だけです（[10-3](#10-3-スワイプ削除を確かめる)）

アプリの画面下部にも、この注意書きを常時表示しています。

安全のために入れてある仕組み:

- **アレルギーは必ずリストの最上部**に、警告色（赤）で表示されます。苦手・好みとは背景色から違います
- **アプリを開いたときは必ず「にがて」から始まります**。前回すきモードだったからといって、食べられないものが隠れた状態で開くことはありません
- **アレルギーの赤は、すきモード（桃色）でも赤のまま**です。配色に合わせて桃に寄せると警告として弱くなるためです
- 同じものを「にがて」と「すき」の両方に入れようとすると警告します（相手からどちらか分からなくなるため）
- レベルは**重い順（3→2→1）**に並びます。見落としてはいけないものが先頭に来ます
- 追加時に**区分とレベルを選ぶまで登録できません**。選び忘れによる誤登録が起きないようにしてあります
- アイコンに絵文字を使っていません（端末によって表示が変わる／欠けるため）

## 1. Supabase プロジェクトを作る

1. <https://supabase.com/> を開き、右上の **Sign in** から GitHub アカウントなどでログインします。
2. ダッシュボードで **New project** を押します。
3. 入力項目:
   - **Name**: `food-ng-share`（何でも構いません）
   - **Database Password**: 自動生成されたものをコピーしてどこかに保管しておきます
     （このアプリでは使いませんが、後で必要になることがあります）
   - **Region**: 🚩 **`Northeast Asia (Tokyo)`** を選んでください

   > **Region は後から変更できません。**
   > 変更するにはプロジェクトを作り直してデータを移す必要があり、かなり面倒です。
   > 日本から使うなら必ず Tokyo を選んでください。

4. **Create new project** を押します。準備が終わるまで1〜2分かかります。

## 2. schema.sql を実行する

テーブル・RLS ポリシー・関数をまとめて作ります。

1. 左サイドバーの **SQL Editor**（⚡アイコン）を開きます。
2. **New query** を押します。
3. このリポジトリの [`supabase/schema.sql`](supabase/schema.sql) を開き、**中身を全部コピー**します。
4. エディタに貼り付けて、右下の **Run**（または `Ctrl` + `Enter`）を押します。
5. `Success. No rows returned` と出れば完了です。

> このスクリプトは何度実行しても同じ結果になります（冪等）。
> あとから修正したくなったら、書き換えてもう一度全部貼って実行すれば大丈夫です。

作られるもの:

| テーブル | 内容 |
|---|---|
| `profiles` | 表示名 |
| `rooms` | 2人組の共有グループ・招待コード |
| `room_members` | 誰がどのルームにいるか |
| `restrictions` | 食べられないもの本体 |
| `heartbeat` | 無料枠の自動停止対策用（GET されるだけ） |

**全テーブルで RLS（Row Level Security）が有効**になり、
「自分の行だけ書き換えられる／同じルームの相手の行は読めるだけ」という制御がかかります。

`restrictions` の1件は次の要素で表します。

| 列 | 意味 |
|---|---|
| `food` | 名前（`えび` のような食材名でも `エビチリ` のような料理名でもよい） |
| `category` | **分類**: `ingredient`=食材 ／ `dish`=料理 |
| `kind` | **区分**: `allergy`=アレルギー ／ `dislike`=苦手・好み ／ `like`=好きなもの |
| `level` | **強さ**（1〜3。大きいほど強い）。意味は `kind` によって変わります（下の表） |
| `note` | 自由記入のメモ |

`level` の読み方:

| 値 | にがて側（allergy / dislike） | すき側（like） |
|---|---|---|
| 3 | 食べられない・苦手 | 大好き |
| 2 | 食べられるが極力避けたい | 好き |
| 1 | 好んでは食べない | まあ好き |

> **「にがて」と「すき」に専用の列は作っていません。**
> `kind` が `like` かどうかだけで決まります。列を増やすと `kind` との整合を
> 保つ制約が必要になり、移行も面倒になるためです。

> **すでに古いバージョンで使っている場合**
> `schema.sql` には移行処理が入っています。**もう一度貼って実行するだけ**で、
> 旧「宗教・信条」は「苦手・好み」へ、旧レベル（絶対NG／できれば避けたい／少量なら大丈夫）は
> 3／2／1 へ自動的に移り、`category` 列が追加されます。データは消えません。

## 3. Realtime の設定を確認する

お互いの編集をリアルタイムに反映させるため、対象テーブルを Realtime の
パブリケーションに登録する必要があります。

**`schema.sql` を実行済みなら、この作業は自動で終わっています。**
念のため確認したい場合は次のようにします。

1. 左サイドバー **Database** → **Publications** を開きます。
2. `supabase_realtime` の行の **Source**（テーブル数のリンク）をクリックします。
3. 次の3つに ✅ が入っていることを確認します。
   - `restrictions`
   - `profiles`
   - `room_members`

> **ここを忘れると、相手の変更が画面に飛んでこなくなります。**
> 「相手が追加したのに自分の画面に出ない」ときは、まずここを疑ってください。

また `schema.sql` では `restrictions` に `replica identity full` を設定しています。
これが無いと **削除だけが相手に伝わらない**（追加・更新は伝わる）という分かりにくい
不具合になります。既に実行済みなら気にしなくて大丈夫です。

## 4. ログイン（メール）の設定をする

このアプリは**マジックリンク（パスワード不要）**でログインします。
メールアドレスを入れると、ログイン用のリンクと確認コードが届きます。

### 4-1. リダイレクト先 URL を登録する

これを登録しないと、メールのリンクを開いても**アプリに戻ってこられません**。

1. 左サイドバー **Authentication** → **URL Configuration** を開きます。
2. **Site URL** に公開先の URL を入れます。
   ```
   https://ユーザー名.github.io/リポジトリ名/
   ```
3. **Redirect URLs** の **Add URL** で、次の2つを追加します。
   ```
   https://ユーザー名.github.io/リポジトリ名/
   https://ユーザー名.github.io/リポジトリ名/**
   ```
   （`**` 付きも入れておくと、パスやクエリが付いた場合に弾かれません）
4. 手元でも動かしたい場合は、これも足しておきます。
   ```
   http://localhost:8000
   http://localhost:8000/**
   ```
5. **Save** を押します。

> まだ GitHub Pages の URL が決まっていない場合は、
> [手順6](#6-github-pages-で公開する) を先に済ませてから戻ってきてください。

### 4-2. メール本文に確認コードを入れる（必須）

スマホではメールアプリの内蔵ブラウザでリンクが開いてしまい、
アプリに戻れないことがあります。その逃げ道として、
**確認コードを入力してログインする**画面を用意してあります。

Supabase の既定のメール本文にはリンクしか入っていないので、コードも出るようにします。

1. **Authentication** → **Emails**（または **Email Templates**）を開きます。
2. **Magic Link** テンプレートを選びます。
3. 本文の末尾に次を追加します。

   ```html
   <p>リンクが開けない場合は、アプリの「メールに届いたコード」欄に次の数字を入力してください。</p>
   <p style="font-size:28px;letter-spacing:8px;"><strong>{{ .Token }}</strong></p>
   ```

   > **コードの桁数は Supabase の設定で 6〜10桁の間で変わります**
   > （Authentication → Sign In / Providers → Email → Email OTP Length）。
   > アプリ側は桁数を決め打ちしていないので、どの設定でもそのまま動きます。

4. **Save** を押します。

### 4-3. 🚩 ホーム画面に追加して使う場合（重要）

スマホのホーム画面にアイコンを置いて使う場合、**ログイン方法が変わります。**

**iOS では、ホーム画面のWebアプリと Safari で保存領域（localStorage）が完全に別々です。**
メールのマジックリンクをタップすると必ず **Safari 側**で開くため、
そこでログインが成立しても**ホーム画面アプリには何も残りません**。
結果として「開くたびに毎回ログイン画面に戻る」ことになります。

**解決策: リンクではなく、確認コードを使ってください。**

1. ホーム画面のアイコンからアプリを開く
2. メールアドレスを入れて「ログイン用メールを送る」
3. **届いたメールのリンクはタップしない**
4. メール本文の**数字のコード**を、アプリの「コードでログイン」欄に入力

コードはアプリの中で入力するので、ホーム画面アプリ自身にログインが保存され、
**次からは開くだけで入れます**（ネイティブアプリと同じ感覚になります）。

アプリ側では、ホーム画面から起動していることを検知して
**自動的にコード入力を主役に切り替え、警告を表示**します。
リンクをタップしてしまう事故が起きにくいようにしてあります。

> この事情があるため、[手順4-2](#4-2-メール本文に確認コードを入れる必須)の
> `{{ .Token }}` の設定は**必須**だと思ってください。
> これを入れていないと、ホーム画面アプリからはログインできません。

### 4-4. ⚠️ メール送信の上限について

**Supabase 組み込みのメール送信には、1時間あたりの厳しい送信上限があります**
（既定では 1 時間あたり数通程度）。開発中に何度もログインを試すと、
すぐに送信が止まって「メールが届かない」状態になります。

アプリ側では次の対策を入れてあります。

- 送信ボタンは**連打できず、送信後60秒はクールダウン**します（ページを再読み込みしてもリセットされません）
- 上限に達した場合、汎用エラーではなく
  **「メール送信の上限に達した可能性があります。しばらく待ってから再試行してください」**と表示します

それでも足りない場合は、**独自の SMTP を設定**すれば上限を上げられます。

- **Project Settings** → **Authentication** → **SMTP Settings** で
  **Enable Custom SMTP** をオンにし、Resend / SendGrid / Amazon SES / Gmail などの
  SMTP 情報を入力します。
- 2人しか使わない用途なら、無料枠の範囲で十分収まります。

## 4-5. プッシュ通知を設定する（任意）

相手が項目を**追加・削除**したときに、スマホへ通知を飛ばせます。
レベルやメモの微修正では通知しません。

**設定しなくてもアプリは普通に動きます。** 空のままなら通知の欄自体が表示されません。

> **iPhone / iPad では、ホーム画面に追加したアイコンから開いたときだけ**通知を使えます
> （[手順4-3](#4-3--ホーム画面に追加して使う場合重要)）。Safari のタブからでは使えません。

### 4-5-1. カギを作る

公開URLに置いてある **`tools/vapid.html`** をブラウザで開き、「カギを作る」を押します。

```
https://ユーザー名.github.io/リポジトリ名/tools/vapid.html
```

3つの値が出ます。**カギはこのページの中だけで作られ、どこにも送信されません。**
設定し終わるまでページを閉じないでください。

| | 何に使うか | 公開してよいか |
|---|---|---|
| ① 公開カギ | `config.js` に書く | ✅ 公開してよい |
| ② 秘密のカギ | Supabase のシークレット | ❌ **絶対に公開しない** |
| ③ 合言葉 | Supabase のシークレットと Webhook | ❌ 公開しない |

### 4-5-2. config.js に①を書く

```js
export const VAPID_PUBLIC_KEY = "①の値";
```

### 4-5-3. Edge Function を作る

**Edge Functions** → **Deploy a new function** → **Via Editor** を選びます。
PCへのソフト導入は不要で、ブラウザだけで完結します。

1. 名前を **`notify-partner`** にする（この名前でないとアプリから呼べません）
2. このリポジトリの [`supabase/functions/notify-partner/index.ts`](supabase/functions/notify-partner/index.ts) の中身を全部貼り付ける
3. **Deploy** を押す

### 4-5-4. シークレットを登録する

**Edge Functions** → **Secrets** で、次の4つを追加します。

| 名前 | 値 |
|---|---|
| `VAPID_PUBLIC_KEY` | ①の値 |
| `VAPID_PRIVATE_KEY` | **②の値** |
| `VAPID_SUBJECT` | `mailto:あなたのメールアドレス` |
| `WEBHOOK_SECRET` | ③の値 |

> `SUPABASE_URL` と `SUPABASE_SERVICE_ROLE_KEY` は Supabase が自動で入れるので、登録不要です。
> service_role キーはこの関数の中（サーバ側）でしか使いません。**フロントには絶対に出しません。**

### 4-5-5. Webhook を作る

**Database** → **Webhooks** → **Create a new hook**

| 項目 | 値 |
|---|---|
| Name | `notify-partner` |
| Table | `restrictions` |
| Events | **Insert** と **Delete** にチェック（Update は外す） |
| Type | **Supabase Edge Functions** |
| Edge Function | `notify-partner` |
| HTTP Headers | `x-webhook-secret` に **③の値** |

### 4-5-6. 動作を確かめる

1. ホーム画面のアイコンからアプリを開く
2. 右上の **⚙（設定）** を開く
3. 「相手の更新を通知」の **通知をオンにする** を押し、許可する
4. **テスト通知** を押す → 数秒で通知が届けば成功

> **届かないとき**は、設定欄に理由が日本語で出ます。
> それでも分からない場合は、**Edge Functions → Logs** に送信結果が残っています。

## 5. config.js に接続情報を書く

1. 左サイドバー **Project Settings**（⚙）→ **API Keys** を開きます。
2. 次の2つを控えます。
   - **Project URL**: `https://xxxxxxxx.supabase.co`
   - **Publishable key**: `sb_publishable_...` で始まる文字列
3. リポジトリの [`config.js`](config.js) を開いて書き換えます。

```js
export const SUPABASE_URL = "https://xxxxxxxx.supabase.co";
export const SUPABASE_PUBLISHABLE_KEY = "sb_publishable_xxxxxxxxxxxxxxxx";
```

### ⚠️ ここでよく間違えるポイント

- **`SUPABASE_URL` には `/rest/v1/` を付けないでください。**
  ダッシュボードには `https://xxxx.supabase.co/rest/v1/` と表示されることがありますが、
  ライブラリが `/rest/v1` や `/auth/v1` を自分で付け足すため、
  付けたままだと `/rest/v1/rest/v1/...` になって全部 404 になります。

- **`sb_secret_...` で始まる secret キーは絶対に書かないでください。**
  secret キーは **RLS を無視してすべてのデータを読み書きできます**。
  フロントエンドにも、リポジトリにも、絶対に置かないでください。
  このアプリは secret キーを一切使いません。

> ℹ️ Supabase は API キーの方式を変更しており、現在は
> **publishable キー**（`sb_publishable_...`）と **secret キー**（`sb_secret_...`）を使います。
> 従来の `anon` / `service_role` キーはレガシー扱いで、**2026年末に廃止予定**です。
> ただし **Postgres 側のロール名は従来どおり** `anon`（未ログイン）/ `authenticated`（ログイン後）
> のままです。キーの名前とロールの名前は別物なので、混同しないでください。
> `schema.sql` の RLS ポリシーが `anon` / `authenticated` と書いてあるのはそのためです。

## 6. GitHub Pages で公開する

git コマンドが使えなくても、**ブラウザだけで完結**します。

### 6-1. リポジトリを作る

1. <https://github.com/new> を開きます。
2. **Repository name** に `food-ng-share` などと入力します。
3. **Public** を選びます（GitHub Pages を無料で使うため）。
4. **Create repository** を押します。

### 6-2. ファイルをアップロードする

1. 作ったリポジトリのページで **Add file** → **Upload files** を選びます。
2. このプロジェクトのファイル一式を、**フォルダごとドラッグ&ドロップ**します。
   （`index.html` / `style.css` / `config.js` / `js/` / `vendor/` / `supabase/` /
   `.github/` / `README.md`）

   > `.github` フォルダはブラウザによっては掴みにくいことがあります。
   > その場合は **Add file** → **Create new file** でファイル名に
   > `.github/workflows/keepalive.yml` と打つと、フォルダごと作れます。

3. 下の **Commit changes** を押します。

### 6-3. Pages を有効にする

1. リポジトリの **Settings** タブ → 左メニューの **Pages** を開きます。
2. **Source** を **Deploy from a branch** にします。
3. **Branch** を `main`、フォルダを **`/ (root)`** にして **Save**。
4. 1〜2分待つと、次の URL で公開されます。

   ```
   https://ユーザー名.github.io/リポジトリ名/
   ```

5. この URL を [手順 4-1](#4-1-リダイレクト先-url-を登録する) の
   **Site URL / Redirect URLs** に登録するのを忘れずに。

### 6-4. 手元で動かしたいとき（任意）

このアプリは ES Modules を使うため、`index.html` をダブルクリックして
`file://` で開くと動きません。簡易サーバーを立ててください。

```bash
python -m http.server 8000
```

そのうえで <http://localhost:8000/> を開きます。

## 7. 友人を招待する

1. 自分がアプリを開き、メールアドレスでログインします。
2. 表示名（例: `はるか`）を入れて **ルームを作成する** を押します。
3. **相手のリスト** タブを開くと、**招待コード**と共有ボタンが出ます。
4. **リンクを共有** を押して、LINE などで相手に送ります。
   （スマホなら OS の共有シートが開きます。使えない場合はクリップボードにコピーされます）
5. 相手はそのリンクを開いて、自分のメールアドレスでログインするだけです。
   自動的に同じルームに参加します。
6. リンクが使えない場合は、**招待コードをコピー**して伝え、
   相手のアプリの「招待コードで参加する」に入力してもらってください。

- 1つのルームに入れるのは **2人まで**です。3人目は参加できません。
- 参加してもらったあとは、**コードを無効化**しておくと安心です。
  （相手のリストタブ → **コードを無効化**。あとから **再発行** もできます）

## 8. publishable キーを公開して大丈夫な理由

`config.js` に書いた URL と publishable キーは、ブラウザの開発者ツールを開けば
誰でも見られます。**それで問題ない設計**になっています。

publishable キーは「**このプロジェクトに話しかけてよい**」という意味しか持ちません。
実際に**どのデータを読み書きできるか**は、すべてサーバー側の
**RLS（Row Level Security）ポリシー**が決めています。

このアプリの RLS は次のようになっています。

| 対象 | 誰が読める | 誰が書ける |
|---|---|---|
| `restrictions`（NG食材） | 同じルームのメンバーだけ | **自分が登録した行だけ** |
| `profiles`（表示名） | 同じルームのメンバーだけ | 自分の行だけ |
| `rooms` | メンバーだけ | 直接は誰も書けない（RPC 経由のみ） |
| `room_members` | 自分が属するルームの行だけ | 参加は `join_room` RPC のみ／退出は自分の行のみ |
| `heartbeat` | 誰でも（読むだけ） | 誰も書けない |

つまり、キーを知っていても**他人の登録を書き換えたり消したりはできません**。
招待コードを知らなければ、そもそもルームの中身は1件も見えません。

> **だからこそ、RLS が唯一の防御線です。**
> テーブルを追加するときは、**必ず RLS を有効にしてポリシーを書いてください。**
> RLS を有効にしていないテーブルが1つでもあると、そこだけ誰でも読み書きできてしまいます。

一方 **secret キー（`sb_secret_...`）は RLS を完全に無視します。**
これが漏れると全データが読み書きされます。フロントエンドにもリポジトリにも置かないでください。

## 9. 無料枠の一時停止と keepalive

Supabase の無料プロジェクトは、**1週間アクセスが無いと自動的に一時停止**されます。
停止すると、ダッシュボードから手動で **Restore** するまでアプリは動きません。
「たまにしか使わない」用途では確実に踏むので、対策を入れてあります。

[`.github/workflows/keepalive.yml`](.github/workflows/keepalive.yml) が
**毎日 UTC 3:00（日本時間 12:00）**に `heartbeat` テーブルへ GET を1本投げます。

### 有効にする手順

1. リポジトリの **Actions** タブを開きます。
2. 「Workflows aren't being run on this forked repository」等の案内が出たら、
   **I understand my workflows, go ahead and enable them** を押します。
3. 左の一覧から **keepalive** を選び、**Run workflow** で一度手動実行して、
   緑のチェックが付くことを確認します。

> **リポジトリの Actions が有効になっていないと動きません。**
> 初回だけ手動で実行して、動作を確認しておいてください。

### ⚠️ さらに気をつけること

- GitHub は、**60日間コミットが無いリポジトリのスケジュール実行を自動的に停止**します。
  2〜3ヶ月に一度でいいので、**Actions タブから手動実行**するか、
  何か小さなコミットをしてください（README に1行足すだけでも十分です）。
- **長期間放置してプロジェクトが停止してしまった場合**は、keepalive では復旧できません。
  Supabase ダッシュボードを開き、プロジェクトの **Restore project** を押してください。
  データは消えていません。数分で復旧します。
- アプリ側でも、停止を検知したときは汎用エラーではなく
  **「サーバーが休止しています。Supabase ダッシュボードで復元してください」**と案内します。

## 10. 動作確認のしかた

### 10-1. RLS が正しく効いているかを確かめる

[`supabase/verify_rls.sql`](supabase/verify_rls.sql) を SQL Editor に貼って **Run** してください。
次のことを実際に試して、結果の表を返します。

- 全テーブルで RLS が有効か
- `security definer` 関数に `search_path` が固定されているか
- 部外者から `restrictions` / `rooms` が1件も見えないか
- 未ログイン（anon）から `heartbeat` は読めるが書けないか
- **ユーザーA としてユーザーB の行を UPDATE / DELETE しようとして、0件で弾かれるか**
- 自分の行はちゃんと更新できるか（ポリシーが厳しすぎないか）
- Realtime のパブリケーションと `replica identity` の設定

**「結果」列がすべて `PASS` か `SKIP`** ならOKです。
`SKIP` は「まだ2人揃っていない／登録が0件」という意味なので、
2人ともログインして1件ずつ登録してから、もう一度実行してください。

> このスクリプトはデータを壊しません。
> 万一 DELETE が通ってしまった場合は、その行を自動的に復元します。

### 10-2. リアルタイム同期を確かめる

1. PC のブラウザで2つのウィンドウを開き、片方をシークレットウィンドウにします。
   （別々のログインにするため）
2. それぞれ別のメールアドレスでログインし、同じルームに入ります。
3. 片方で食材を追加すると、**数秒以内**にもう片方の「相手のリスト」に出れば成功です。
4. 相手が同時に開いていると、画面上部に「〇〇さんが表示中」と出ます。

出てこない場合は [手順3](#3-realtime-の設定を確認する) を確認してください。

### 10-3. スワイプ削除を確かめる

1. **マイリスト**（または**まとめ**）で、自分が登録した項目を**左に大きくスワイプ**します。
2. 背面に赤い「削除」が出て、指を離すとその場で消えます。
3. 画面下に **5秒間だけ「元に戻す」** が出ます。押すと復活します。
   アレルギー項目を消したときは、この帯が**赤くなって目立つ**ようになっています。

確認しておきたい挙動:

- 少しだけ横に動かして離した場合は**消えない**（誤操作防止のため、64px以上引く必要があります）
- 斜めや縦に動かした場合は**普通の縦スクロールになる**（消えない）
- **相手の項目はスワイプできない**（サーバー側の RLS でも他人の行は消せません）
- 軽くタップした場合は、これまでどおり**編集画面が開く**

> ⚠️ 削除に確認ダイアログは出ません。**5秒の「元に戻す」を逃すと戻せません。**
> 消えて困る項目は、編集画面から内容を控えてから消してください。

### 10-3. オフライン復帰を確かめる

1. 開発者ツール（F12）の **Network** タブで **Offline** にします。
2. 画面上部の表示が「オフライン」に変わります。
3. **Offline** を解除すると「接続中」に戻り、**自動で最新データを取り直します**。
4. オフライン中に行った操作は失敗としてロールバックされ、日本語のエラーが出ます。

## 11. 困ったときは

| 症状 | 原因と対処 |
|---|---|
| 画面に「セットアップが未完了です」と出る | `config.js` がプレースホルダのままです。[手順5](#5-configjs-に接続情報を書く)へ |
| すべての通信が 404 になる | `SUPABASE_URL` の末尾に `/rest/v1/` が付いていませんか |
| 「Could not find the table 'public.xxx'」 | `schema.sql` をまだ実行していません。[手順2](#2-schemasql-を実行する)へ |
| メールが届かない | 迷惑メールを確認。それでも来なければ送信上限です。1時間ほど待つか、独自SMTPを設定してください（[手順4-4](#4-4-️メール送信の上限について)） |
| リンクを開いてもログイン画面に戻る | Redirect URLs の登録漏れです（[手順4-1](#4-1-リダイレクト先-url-を登録する)）。メール本文の確認コードでもログインできます |
| 「ログインリンクの有効期限が切れています」 | マジックリンクには有効期限があります。もう一度送信してください |
| 相手の変更が反映されない | Realtime のパブリケーション設定漏れです（[手順3](#3-realtime-の設定を確認する)） |
| 追加・更新は届くのに削除だけ届かない | `alter table public.restrictions replica identity full;` を実行してください |
| 相手が参加したのに招待画面のままになる | `room_members` が Realtime に登録されていません（[手順3](#3-realtime-の設定を確認する)） |
| 「サーバーが休止しています」と出る | 無料枠の自動停止です。ダッシュボードから **Restore project**（[手順9](#9-無料枠の一時停止と-keepalive)） |
| `infinite recursion detected in policy` | `room_members` のポリシーが `room_members` を直接参照しています。`schema.sql` の `is_room_member()` 経由に直してください |
| 3人目が参加できない | 仕様です。1ルームは2人までです |

### アイコンに絵文字を使っていない理由

同じ絵文字でも OS やフォントによって見た目が大きく変わり、端末によっては
豆腐（□）になります。**アレルギーの警告に環境依存の記号を使うのは危険**なので、
必要な形だけを線画の SVG として [`js/icons.js`](js/icons.js) に持っています。
外部のアイコンライブラリも読み込みません。

色は `currentColor` に従うので、CSS変数を変えるだけでアイコンの色も一緒に変わります。

### supabase-js を同梱している理由

`vendor/` に supabase-js v2.58.0 を依存ごと取り込み、
import を相対パスに書き換えてあります。**実行時に CDN を参照しません。**

CDN 依存だと、CDN 障害・社内ネットワークのブロック・バージョン変更で
ある日突然アプリが動かなくなります。2人だけで細く長く使う道具なので、
外部依存はゼロにしてあります。

CDN 版に切り替えたい場合は [`vendor/supabase-js.js`](vendor/supabase-js.js) の
最終行を次に差し替えるだけです。

```js
export * from "https://esm.sh/@supabase/supabase-js@2.58.0";
```
